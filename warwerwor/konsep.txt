2. POLA KERJA, CARA BERPIKIR, DAN PERILAKU (WAJIB DIJAGA)
================================================================================

a. KLAIM KEBENARAN HANYA LAHIR DI VALIDATOR. Recon = fakta, Threat =
   hipotesis, Attack = skenario. Tidak ada yang boleh mengklaim bug nyata.
   Status tidak pernah dinaikkan: PROVEN > INFERRED > POSSIBLE > UNKNOWN.
   Attack agent bahkan menulis eksplisit "does not claim confirmation".

b. SETIAP KLAIM TERTELUSUR MUNDUR: attack step → chain stage → fact id →
   baris sumber. Tidak ada klaim tanpa jejak.

c. INCONCLUSIVE ≠ REJECT. Compile error / timeout / harness hilang =
   kegagalan infrastruktur, BUKAN bukti menolak hipotesi. Hanya kegagalan
   eksekusi nyata (call revert / attacker tidak gain) yang boleh REJECT.

d. GENERIK MUTLAK: engine TIDAK boleh mengandung nama protokol/benchmark
   (jackpot/megapot/usdc/dll). Di-guard test otomatis di tiap agent —
   guard pernah menangkap kata "warden" di docstring engine sendiri.
   Nama protokol hanya boleh ada di DATA (input/harness/laporan).

e. DISIPLIN KECURIGAAN: dinamis ≠ terkontrol attacker; external call ≠
   reentrancy; adjacency ≠ kausalitas; ADA check ≠ aman (selalu tanya:
   check itu mengukur APA? — inilah asal temuan cross-asset blind spot:
   check menjaga aset A, pencurian terjadi di aset B yang tak diukur).

f. SPLIT ENGINE vs HARNESS (kunci generisitas validator): engine
   meng-generate attacker generik + driver + assertion; harness (DATA
   eksternal per-repo, file contracts_X_sol__fungsi.sol atau
   contracts_X_sol.sol) yang tahu cara deploy protokol & memanggil entry.
   Harness hilang → INCONCLUSIVE + scaffold di-generate otomatis dgn TODO
   terisi data attack. Hasil LLM/human mengisi scaffold = LLM-PROPOSED,
   tetap wajib diverifikasi validator.

g. REPO TARGET TIDAK PERNAH DIMODIFIKASI. Workspace forge terisolasi
   (symlink + remappings otomatis + via_ir) ada di dalam folder run.

h. REFERENSI CARA BERPIKIR: code4rena-warden-report/Megapot.md dipakai
   sebagai RUBRIK PENALARAN (5 pola: komposisi dua fitur by-design; bedah
   scope check; callback sebagai timing; cross-asset; entry legal) —
   BUKAN target hardcode. Pipeline sudah mereproduksinya murni generik.

i. STATUS SEMUA AGENT (2026-08-17): 6/6 SELESI + TERUJI —
   recon, threat, attack, validator, finding, orchestrator(maestro).
   Rincian pengujian: unit test per agent (74/16/14/10/10) + E2E: twin
   generik (CONFIRM & REJECT) + jackpot asli via satu perintah maestro
   (10189 facts → 518 hyp → 24 attack → 3 CONFIRM → 3 finding).

j. JEBAKAN YANG SUDAH DIBAYAR (jangan ulangi):
   1. Python 3.14: shutil.isdir dihapus → os.path.isdir.
   2. forge --json: {"path:Contract":{"test_results":{name():{status:
      "Success"|"Failure"}}}} (status kapital).
   3. Kontrak jackpot butuh via_ir+optimizer (stack too deep).
   4. vm.sign(key) ≠ address(uint160(key)); pakai vm.addr(key).
   5. IERC721.safeTransferFrom overload → pakai interface 3-arg khusus.
   6. solady _mint tidak cek receiver; hook hanya di safeTransferFrom.
   7. Patch "revoke allowance SETELAH call" TIDAK menutup celah (drain
      terjadi DI DALAM call) — validator benar tetap CONFIRM; patch benar
      = blacklist target aset protokol (SEBELUM jendela) → REJECT.
   8. Harness dipilih PER-FUNGSI dulu (kontrak__fungsi.sol), fallback
      kontrak ditandai harness_scope=contract + Scope note di finding.
   9. Modul agent dijalankan `python -m pkg.cli` → cwd WAJIB folder
      agent-nya sendiri (maestro sudah mengatur; manual = cd dulu).
   10. Template Solidity di Python .format: { } literal → {{ }}.
   11. Path absolut di artefak (verdict) cepat usang → finding agent
       menghitung ulang path dari validator_dir.

k. HOOK LLM OPSIONAL (adviser, tidak pernah menaikkan bukti):
   - Slot SESI/CLI tanpa API key: AGENT_FINDER_LLM_CMD="perintah" —
     prompt via STDIN, jawaban via STDOUT. Catatan jujur: login email
     ZCode = sesi aplikasi desktop, BELUM ada CLI headless (2026-08-17);
     kredensial ~/.zcode/ privat & tidak pernah diekstrak. Begitu ada CLI
     headless (ZCode/claude/gemini/model lokal), tinggal set env var ini.
   - Slot API key (kompatibel OpenAI): AGENT_FINDER_LLM_API_KEY +
     BASE_URL + MODEL.
   - Tanpa keduanya: DORMANT — pipeline tetap jalan penuh deterministik.

3. PERINTAH UNTUK USER — DARI MULAI SAMPAI AKHIR
================================================================================

>>> LANGKAH 0 — pahami dulu: satu target audit = satu siklus penuh.
    Semua output hidup di runs/<nama-target>/ — JANGAN taruh di /tmp.

>>> CARA #1 (PALING CEPAT — pakai ini kalau tidak mau ribet):
    cd orchestrator
    .venv/bin/python -m maestro <path-repo-target> [opsi]
       --name <run>      nama folder run (default: nama folder repo)
       --limit N         validasi top-N attack saja (default 3; 0 = semua)
       --harness <dir>   folder harness (default validator_agent/validator-harnesses)
       --clean-run       hapus run dir lama dulu (WAJIB kalau run sudah ada)
       --no-tui          output polos (untuk pipe/CI)
    Contoh jackpot:
       .venv/bin/python -m maestro ../benchmarks/code4rena/jackpot \
           --name jackpot-e2e --clean-run
    Hasil: TUI live 5 tahap → ringkasan akhir → laporan di
    runs/<run>/finding/finding-F-XXX.md

>>> CARA #2 (TAHAP DEMI TAHAP — untuk debug/mempelajari):
    # 1. fakta dari repo:
    cd recon-system && .venv/bin/python -m recon.cli <repo> -o ../runs/<t>/recon
    # 2. hipotesis:
    cd ../threat_agent && .venv/bin/python -m threat.cli \
        ../runs/<t>/recon -o ../runs/<t>/threat
    # 3. jalur serangan:
    cd ../attack_agent && .venv/bin/python -m attack.cli \
        ../runs/<t>/recon ../runs/<t>/threat -o ../runs/<t>/attack --clean
    # 4. bukti / bantah (forge nyata):
    cd ../validator_agent && .venv/bin/python -m validator.cli \
        ../runs/<t>/attack <repo> --harness validator-harnesses \
        -o ../runs/<t>/validator --clean [--limit N]
    #    (kalau INCONCLUSIVE/BLOCKED_NO_HARNESS: scaffold harness sudah
    #     ditulis otomatis ke validator-harnesses/ — isi TODO-nya, rerun)
    # 5. laporan:
    cd ../finding_agent && .venv/bin/python -m finding.cli \
        ../runs/<t>/attack ../runs/<t>/validator -o ../runs/<t>/finding --clean

>>> LARIKAN TEST SEMUA AGENT (sebelum/sesudah ubah kode):
    cd threat_agent    && .venv/bin/python -m pytest -q    # 74 test
    cd ../attack_agent && .venv/bin/python -m pytest -q    # 16 test
    cd ../validator_agent && .venv/bin/python -m pytest -q # 14 test
    cd ../finding_agent   && .venv/bin/python -m pytest -q # 10 test
    cd ../orchestrator    && .venv/bin/python -m pytest -q # 10 test

>>> LIHAT / VERIFIKASI TEMUAN:
    cat runs/<t>/finding/finding-F-001.md                 # laporan akhir
    cat runs/<t>/validator/verdicts.jsonl                 # verdict per attack
    cd runs/<t>/validator/workspace/<attack-id>           # PoC forge
    forge test --match-path "test/Validate*.t.sol" -vvvv  # jalankan ulang PoC

>>> SETELAH SELESAI / SEBELUM TARGET BARU (WAJIB):
    rm -rf runs/<target-lama>/        # atau arsip:
    tar -czf archive/<t>-$(date +%F).tar.gz runs/<t>/
    Mengapa: artefak tahap = input tahap berikutnya; artefak target lama
    yang tersisa bisa terbaca target baru (kontaminasi lintas protokol).

>>> SISA PEKERJAAN (kalau mau lanjut mengembangkan):
    - Loop REJECT otomatis di maestro (sekarang retry_hint manual/LLM)
    - Coverage validator lebih luas (gain di TX terpisah, invariant fuzz)
    - Uji benchmark lain (Initia/Monetrix di code4rena-warden-report/) —
      ingat pembersihan antar-target
    - ATURAN: setiap perubahan/claim sukses WAJIB dibuktikan test/run dan
      dicatat di log (lihat pola catatan di git history konsep.txt versi
      sebelumnya; simpan bukti = perintah + angka).

  benchmarks/<repo> ──(dibaca, tak diubah)──> runs/<t>/recon
  runs/<t>/recon ──> runs/<t>/threat ──> runs/<t>/attack
  runs/<t>/attack + benchmarks/<repo> + validator-harnesses/
      ──> runs/<t>/validator (termasuk workspace/ forge terisolasi)
